01 · The problem

The model is four times the machine

GLM-5.3-Flash is a mixture-of-experts model: 321 billion weights, of which about 18 billion fire for any one token. Every expert still has to sit in memory, because the next token may need any of them.

The Mac has 128 GB, and it is also the machine for the editor, the builds and Claude Code. So we set a hard rule: the model process gets at most 84 GB, and at least 45 GB stays free.

Turn the knob on the scale. A plain 4-bit quantization still weighs 168 GB. Getting under the line took three more steps.

02 · Calibrate

First, watch it do our work

Generic quantizers calibrate on Wikipedia. We built 712 samples from the work this Mac actually does: GitHub files and commit edits, multi-turn agent traces with real tool calls, competition math, and 16K to 64K-token documents. 512 drive calibration; 200 are held out for scoring.

The 305 GB checkpoint never fits, so calibration streams it one layer at a time: load, run every sample through, record, free. For each layer it records how often each expert is chosen, how much it contributes, and how much error every tensor takes at 2 to 8 bits.

03 · Prune

Keep 153 of 288 experts in every layer

Each layer's router sends a token to 8 of its 288 experts. Some are busy, some almost idle. Removing the quiet ones cuts 47% of the expert weight.

We ranked experts with REAP, which scores how much an expert changes the output when it is chosen. The figure is real data from layer 20: sort height is how often the router picked each expert while it read our samples, and the stick in front shows the 8 picked for each new token.

Switch to "Busiest 153" and the kept share of traffic rises from 54% to 70%. That gap was our first surprise, and the third detour below.

04 · Quantize

Spend bits where the errors are

A uniform 4-bit model treats an attention projection and a rarely used expert the same. We gave each of 490 tensor groups its own width from the measured errors, with a solver that minimises total error under a 76 GB budget. The average came out at 3.48 bits per weight.

Then we changed how each group is rounded. Instead of taking a scale from the group's minimum and maximum, we search the clipping range and solve a least-squares fit weighted by how strongly real inputs use each channel. Same bytes, 10.5% less divergence from the full model: the largest single gain of the project.

05 · Detours

Six things we believed that measurements overturned

Most of the time went into finding out why a number looked wrong. Each card is a belief we started with, struck through, and what we found instead.

Evaluation

A mean KL of 2.9 means the build is broken.

The error lives where the model reads, not where it writes.

Split by chat role, assistant tokens sat at KL 0.12 with 92% top-1 agreement. User and tool positions run at KL 3 to 7 for every build, the reference included, because no chat model predicts your prompt word for word.

Precision

Recalibrating in fp32 will fix it.

fp32 measured no better than bf16.

Splitting the metric by role made a five-hour fp32 recalibration pointless. We ran a slice anyway to be sure.

Pruning

REAP saliency picks the right experts.

On GLM, REAP scores are almost flat.

Median 5.7 against a cutoff of 5.5. The 153 it keeps carry 54% of routing on average, where the busiest 153 would carry 68%.

Rounding

Pruning choices matter most.

How you round matters more than what you cut.

Refitting every scale and bias by importance-weighted least squares cut assistant KL 10.5% at the same size. Pruning variants moved it 2 to 3%.

Recovery

Fixing every layer locally fixes the model.

All 45 layers improved; the model did not.

Blockwise distillation lowered every layer's error and nudged assistant KL to 0.106, but read prompts worse and coded slightly worse. We shipped the simpler build.

Engineering

The trainer's memory is fine.

It leaked 1.46 GB per layer.

MLX keeps a custom function's inputs alive, so each layer's expert weights stayed pinned: 110 GB projected by layer 43. Fixed, it ran flat at 24 GB, and sparse layers went from 17 minutes to 2.

06 · Where it lands

Sonnet-class at the effort people actually use

Most people run hosted models at their default, medium reasoning effort, so that is the comparison here. On the Artificial Analysis Intelligence Index, the original GLM-5.3-Flash scores 42: one point above Claude Sonnet 5.5 at medium, and six below GPT-6.1 Sol at medium.

Those are the original model's scores. GLM 5.3 Flash-sauhard matches it on 92.4% of next tokens, so expect a point or two lower until someone runs the suite on it. On our own tasks it scored 95% on HumanEval+, 92.5% on MBPP+, 84.8% on 105 tool calls and 97.5% on MATH-500 problems.

07 · The open field

Against everything else built for a 128 GB Mac

We surveyed what people have published on Hugging Face for this class of machine. GLM-5.3-Flash is the highest-ranked open model that fits at all, and every other public build of it is either far larger or reports lower fidelity. At an 80 GB budget we found nothing clearly better than GLM 5.3 Flash-sauhard.

The strongest challenger is a different model: ISTA-DASLab's 3-bit Qwen3.8-Flash-Next, 84 GB, matching its full-precision parent on its authors' task suite. Its base model scores two points lower than the base of GLM 5.3 Flash-sauhard, which is close to noise, so it is the next build we will test head to head.

08 · Run it

A dashboard, two models, nothing in the cloud

A launchd service keeps a local control panel up. Start, stop or switch between GLM and a tuned Qwen3.8-Flash-Next profile, watch memory, and point any OpenAI- or Anthropic-compatible client at it, Claude Code included.

The server clamps how much memory it may pin, caps itself at 84 GB, and skips a prefill copy that costs 22 to 24 GB at 32K context without changing a single output token.

  • Speculative decoding with GLM's own draft head is built in but not yet verified, so 41.5 tok/s is plain decode.
  • Long-context retrieval at 64K to 128K has not been measured on this build.
  • The index score for GLM 5.3 Flash-sauhard is inferred from its fidelity, not measured.
